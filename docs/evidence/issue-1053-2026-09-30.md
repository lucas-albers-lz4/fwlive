# Direct read-helper execution — #1053 / #980

The maintainer selected direct execution after the #980 comparison. This
candidate removes `coreutils-timeout`, provider discovery, GNU/BusyBox wrappers,
process-group draining, missing-provider diagnostics, and provider-specific UI
recovery. It never selects a timeout provider, including when one is installed.
No replacement watchdog or runtime dependency is introduced.

Input validation, read/write ACL separation, temporary-file guards, ordinary
command errors, map/line/name/count limits, adaptive polling, and WAN lock and
rollback safeguards remain. The resolver elapsed budget only controls whether
to start another lookup; it cannot interrupt the current helper.

## Reliability boundary

Removing fwlive's deadlines does **not** remove rpcd's existing execution timer.
All three stock guests below ran `/sbin/rpcd ... -t 30`, with UCI timeout 30.
The SDK's pinned rpcd sources confirm that the execution-timeout callback sends
SIGKILL to the plugin PID, rather than its process group. The upstream compiled
default is 120 seconds when no configured override is supplied; the checked
stock OpenWrt configuration supplies 30. These are rpcd controls, not fwlive
termination guarantees.

A finite 35-second log-read fixture, called through a temporary rpcd object
with the client timeout raised to 45 seconds, returned a nonzero/no-response
result after **30.110 / 30.128 / 30.122 seconds** on 23.05 / 24.10 / 25.12.
Immediately afterward the plugin PID was gone and its helper PID was alive.
The fixture ended naturally; no infinite fault was left running. This proves
the stock plugin-process boundary and the loss of descendant containment.
Direct CLI invocation has no rpcd timer.

Finite slow-helper probes returned successful log and nft results after about
**6.1–6.2 seconds**, and a positive DNS name after **2.1 seconds**, on all three
guests. A sentinel timeout executable in the fixture PATH was never invoked.
These use branch-helper copies in temporary RPC objects with controlled
service stubs. The DNS fixture overrides the shell function only in the
harness because BusyBox applet preference can bypass PATH stubs. They are
mechanism probes, not native DNS latency measurements or indefinite-stall
recovery guarantees.

The accepted loss is shorter recovery deadlines and descendant cleanup. A
helper can outlive its RPC request; repeated failures can leave extra processes
or temporary files. Real user reliability reports are the trigger to reconsider
a timeout dependency. No claim is made that direct execution has the old
containment guarantees.

The #950/#953 safety properties do not depend on GNU timeout. Hostname liveness
assumes a pending reply eventually arrives; it does not prove runtime helper
termination. WAN lock acquisition retains its independent bounded nonblocking
retry loop. No Lean proof artifact was involved in this change.

## Limits and validation setup

These checks cover x86 KVM guests, not ARM/MIPS hardware, sustained resource
exhaustion, loaded-router scheduling, or all DNS/network failure modes. The
full host suite was run with guests stopped because its forced-stop lifecycle
fixture assumes no live QEMU guests. Final package validation used fresh images:
an earlier repeat-install attempt exposed an existing artifact-only lab helper
ordering problem (it deletes the logging helper before opkg invokes prerm), so
that failed attempt is not counted as a successful upgrade/reinstall test.

Raw logs, probe scripts/results, image provenance, artifact hashes and checksum
manifest are retained in `out/evidence/issue-1053-2026-09-30/` in the implementation
worktree. Large VM images and caches are excluded from the evidence bundle.
All disposable guests were shut down after validation. No release/version bump,
merge, or post-draft model/bot/human review has been performed.
