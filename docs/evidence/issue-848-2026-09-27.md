# Issue #848 — version-changing APK upgrade keeps WAN log — 2026-09-27

Verify-then-close for the APK upgrade residual recorded in #846 items 1
and 48. The user guide already said WAN zone `log` stays on across
upgrades. Host tests model opkg `upgrade` and `PKG_UPGRADE=1` as skip
restore. QEMU had covered uninstall restore and same-version APK
`--force-reinstall`, not a version-changing `apk add` of a newer
`luci-app-fwlive`.

## Guest

OpenWrt 25.12.5 x86_64 QEMU (`Linux OpenWrt 6.12.94`,
`apk-tools 3.0.5`), hostfwd SSH 2223.

Artifacts (existing lab builds; hook body of the *old* package is not
the point — apk did not invoke `pre-deinstall`):

- `out/x86_64/25.12.5/fwlive/luci-app-fwlive-0.1.43-r1.apk`
- `out/x86_64/25.12.5/fwlive/luci-app-fwlive-0.1.44-r1.apk`

## Steps

1. Fresh guest, `luci-app-fwlive` not installed, no
   `/etc/fwlive/wan-log-baseline`.
2. `apk add --allow-untrusted` 0.1.43-r1 (`post-install` only).
3. `./scripts/qemu-reset-wan-logging.sh` then
   `ubus call fwlive enable_wan_logging`.
4. `apk add --allow-untrusted --verbose` 0.1.44-r1.

## Result

| Check | After enable | After 0.1.43 → 0.1.44 |
| --- | --- | --- |
| `firewall.@zone[1].log` | `1` | `1` |
| `/etc/fwlive/wan-log-baseline` | present | present |

apk verbose:

```
(1/1) Upgrading luci-app-fwlive (0.1.43-r1 -> 0.1.44-r1)
  Executing luci-app-fwlive-0.1.44-r1.post-upgrade
```

No `pre-deinstall`. `logread` has the enable notice only.

## Why the hook cannot restore on this path

apk-tools 3.0 `apk_db_install_pkg` runs `APK_SCRIPT_PRE_DEINSTALL` only
when `newpkg == NULL` (uninstall / `apk del`). A replace/upgrade uses `PRE_UPGRADE` on
the new package (OpenWrt emits that script only when `Package/preinst`
exists; fwlive has none) then `POST_UPGRADE` with `PKG_UPGRADE=1`.
OpenWrt `package-pack.mk` maps `Package/prerm` to `pre-deinstall`.

Same-version `apk add --force-reinstall` was already
`post-upgrade`-only ([#389 evidence](issue-389-2026-09-20.md)). This
cell is the missing version-changing pair.

The installation sentence is correct. #848 is not a defect.
